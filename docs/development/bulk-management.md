# 一覧絞り込みと一括状態変更

Tracking: [Issue #28](https://github.com/rytich/play-cms/issues/28) / [PR #29](https://github.com/rytich/play-cms/pull/29)

## 操作範囲

管理画面の動画一覧では、タイトル部分一致またはFilmaファイルID完全一致、公開設定、公開期間の重なりで絞り込める。動画ごとの閲覧用キー一覧では、管理用ID、有効設定、利用状態、発行期間で絞り込める。条件は「検索」で確定し、URLへ保存されるため、検索URLには管理上の情報が含まれ得る。URLを共有しない。

一覧は作成日時とIDの降順で100件ずつ表示する。チェックボックスで現在のページだけを選択し、動画は「公開にする／非公開にする」、未使用キーは「有効にする／無効にする」を選ぶ。確認を取り消した場合は変更しない。成功後は選択を解除して同じ条件を再取得する。通信断などで成否不明の場合は自動再送せず、状態を再取得して確認する。

動画の`published`は管理上の公開設定だけで、実配信・再生は停止中である。キーの無効化は未使用キーの引換設定だけを変え、付与済み視聴権を削除しない。永久取消済みキーは選択不可で、終了済み動画のキーは再有効化できない。現schemaには引換・`redemptions`・視聴権がないため「使用済み」は0件であり、実引換と視聴の確認は未実装である。

## migrationと復元

`0002_admin_bulk_management.sql`は動画へ`published`を、閲覧用キーへ`is_enabled`を追加し、既存行・外部キー・unique・CHECK・索引を保持する。適用前に対象ローカルD1を停止し、公式Wranglerのexport等で別ディレクトリへバックアップを取得して、バックアップの読取可能性と対象を確認する。データ入りDBへの適用はこの実装作業に含めない。

復元が必要な場合は、成否不明のDBへ逆向きSQLを重ねず、サービスを停止した上で検証済みの適用前バックアップ全体から戻す。実データへの適用・復元は対象、バックアップパス、影響を提示して別途承認を得る。

## 合成環境での確認

旧`0001` schemaだけを適用した専用D1で、複数動画と有効・取消済みキーを作成し、全列・制約・索引の保持と、意図的に失敗させたmigrationのrollbackを確認した。別の専用Wrangler stateでも`0001`と`0002`のローカル適用に成功した。

専用ブラウザcontextと別ポートの合成D1へ動画1,001件・一動画のキー1,001件を用意し、100件/最終1件、検索、ページ移動、選択解除、確認中止と実行、動画公開設定、キー100件の無効化・再有効化、取消済み選択不可、URL再読込・戻る進む・編集からの条件復帰、小画面、キーボード操作、通信断案内、ログアウト時の保護情報消去、外部通信0を確認した。

独立レビュー後の合成回帰では、絞り込み中・後続ページでキーを発行しても生キーの一時表示だけを追加し、履歴一覧は現在のURL条件で再取得することを確認した。一括変更で先頭ページが0件になっても結果を表示し、後続ページが0件になった場合は条件を保って先頭へ戻った理由を表示する。日時URLは実在する暦日だけを受理し、タイムゾーンと秒未満をUTCへ正規化した上で、D1の整数秒との包含境界を維持する。

実200%拡大と実BFCache復帰は[Issue #30](https://github.com/rytich/play-cms/issues/30)の公開前必須確認に残す。実Filma、実引換、視聴権、再生、デプロイ、Cloudflare無料枠適合は確認していない。
