## 目的

Filma上の動画を、管理者が公開期間と使い切り閲覧キーで限定共有できる、簡易なCMSを提供し、ライセンス決定後のオープンソース化を目指す。最初のプロトタイプでは機能を増やさず、管理者から視聴者の再視聴までを3〜5名で実際に確認する。

## 利用者と主要機能

### 動画管理者

- 一名の管理者として初期登録、ログイン、ログアウトできる。
- Filma APIキーを一度設定し、接続状態を確認できる。キーはサーバー側で暗号化して保持し、保存後は再表示しない。
- Filmaでアップロード済みの動画をFilmaファイルID、タイトル、説明、公開状態、公開開始・終了日時で登録・編集できる。
- 閲覧キーを必要な数だけ一件ずつ発行できる。キーは一人一コードの使い切りとし、一度だけ表示する。
- 動画は100件単位、閲覧キーは動画ごとに100件単位で表示し、検索・条件絞り込み・複数選択を利用できる。
- 動画は公開／非公開、未使用キーは有効／無効を最大100件ずつ一括変更できる。

管理者プロフィール、複数管理者、アクセス解析、DRM、サムネイル、字幕はP0に含めない。

### 動画視聴者

- 動画固有の`/v/:publicId`を開くと、動画情報を表示する前に閲覧キーを求められる。
- 有効なキーは一度だけ使用できる。直列・並行要求、別ブラウザーからの再利用を拒否する。
- 未ログインでキーを使用した場合は30分間の匿名視聴を開始し、「期限内に登録またはログインしないと二度と閲覧できない」と明示する。
- 匿名視聴中に登録またはログインすると、その動画の視聴権をアカウントへ一度だけ引き継ぐ。
- ログイン済みでキーを使用した場合は、同じ処理で視聴権をアカウントへ付与する。
- ログイン後の`/library`には、本人が取得した視聴権のうち、現在公開中かつ期限内の動画だけを表示する。
- 動画が非公開、公開前、期限終了後の場合は、URLからのアクセス、一覧件数、タイトル、説明、サムネイル、Filma ID、再生情報を表示しない。

メール所有確認、メール送信、パスワード再設定はP0に含めず、招待試験ではテスト用のメールアドレスだけを使う。

## URLと画面遷移

主要な機能・コンテンツ・編集対象は、意味のある固有URLで識別する「URLアドレス可能な画面設計（addressable navigation）」を必須とする。画面遷移を伴う操作はHistoryへ反映し、直接表示、再読み込み、戻る、進むで同じ場所を復元する。同一GET画面内だけで完結させるのは、入力補助、絞り込み、選択、確認表示などの一時的操作に限定する。

## Filma連携と秘密情報

- 長期間有効なFilma APIキーを視聴者のブラウザーへ配布しない。管理者が設定画面へ入力する通信以外では、ブラウザーへ返さない。
- P0の動画アップロードはFilma管理画面で行い、play-cmsには既存のFilmaファイルIDを登録する。
- 将来CMSからアップロードするときも、動画本体はアップロード端末からFilmaへ直接送る。CMSサーバーへの一時保存や二重転送は行わない。
- 将来の直接アップロードは、Filmaが発行する短時間・単一ファイル・アップロード専用の署名URLまたはupload sessionを使う。現在の`fullaccess` APIキーをブラウザーへ渡す方式は採用しない。
- Filmaの実APIは固定した許可先だけへ、サーバーからタイムアウト・応答量・redirectを制限して接続する。

実再生は[Filma再生契約 Issue #16](https://github.com/rytich/play-cms/issues/16)で、動画単位の期限、CMS指定期限を超えないこと、許可ドメイン外で利用できないことを確認できた場合だけ有効にする。確認できない状態で閲覧キーを消費しない。

## 実行環境

- 推奨環境はCloudflare Workers、D1、Web Crypto、React/Vite、Honoとする。
- P0はCloudflareの専用D1とWorkerへ手動デプロイし、招待した3〜5名だけで確認する。
- 一般公開、本番Filma組織、実顧客データ、課金、独自ドメイン、監視基盤、SLAはP0に含めない。
- 完成版は、Node.jsとSQLiteまたはPostgreSQLのadapterを追加し、さくらやロリポップ等のNode.jsを実行できる国内サーバーへ移植可能な境界を維持する。
- Payload CMSは採用しない。Cloudflareでの構成と費用を小さく保つため、軽量な独自coreとadapter方式を採用する。[ADR 0001](../decisions/0001-use-lightweight-portable-architecture.md)

## P0招待テストの完了条件

1. [Issue #35](https://github.com/rytich/play-cms/issues/35)で、キー消費、匿名視聴、登録／ログイン時の権利引き継ぎ、再視聴を一本につなぐ。
2. [Issue #30](https://github.com/rytich/play-cms/issues/30)で、実BFCache復帰と200%拡大を確認する。
3. [Issue #36](https://github.com/rytich/play-cms/issues/36)で、専用Cloudflare D1へmigrationを適用し、招待テスト用Workerへデプロイする。
4. [Issue #37](https://github.com/rytich/play-cms/issues/37)で3〜5名が操作し、80%以上が補助なしで「キー入力から再生」まで完了する。
5. 期限終了後の全視聴者経路で、アクセスとメタデータ取得を拒否する。

テスト結果には人数、成功工程、失敗工程、改善点だけを記録する。メールアドレス、閲覧キー、Cookie、APIキー、Filma ID、再生URL、API応答本文はGitHubへ記録しない。
