- 状態: 承認済み
- 作成日: 2026-09-07
- Tracking: [GitHub Issue #10](https://github.com/rytich/play-cms/issues/10)
- 前提: [基盤設計](2026-09-03-foundation-design.md)
- 実装計画: [P0 Prototype Implementation Plan](../plans/2026-09-07-p0-prototype-implementation.md)
- セキュリティ正本: [`SECURITY.md`](../../../SECURITY.md)
- 先行実装の承認追補: [管理機能プロトタイプ / Issue #18](../../development/admin-first-prototype.md)

## 目的

完成版の基盤を順番に作り切る前に、実際の動画共有フローを小さく動かし、play-cmsが利用者の課題を解決するか検証する。P0は公開製品ではなく、専用のFilmaテスト組織と3〜5名の招待テスターで使う検証用プロトタイプとする。

P0で確認する中心価値は次の一文に限定する。

> 管理者が既存のFilma動画を登録して一度だけ使えるコードを渡し、視聴者が安全に動画を再生し、登録後は期限内の視聴権を再利用できる。

## アプローチの比較と決定

### 採用: Cloudflare限定の実動縦切り

管理者登録、既存Filma動画の登録、コード発行、視聴、視聴者登録、再ログイン後の一覧までを一本につなぐ。外部APIとアクセス制御の主要リスクを早期に検証でき、利用者が実際に触れる。

### 不採用: UIモックを先に完成させる

最短で画面を見せられるが、Filmaの再生契約、使い切りコード、期限判定という最大の不確実性が残る。必要な場合は紙芝居ではなく実動画面の粗いUIを使って改善する。

### 延期: 完成版の基盤Taskを順番に実装する

CloudflareとNode.jsの同時対応、Docker、CI、配布ボタンまで先に完成させる方法は堅実だが、利用者価値の検証が遅い。P0で価値を確認した後に完成版へ戻す。

## 成功条件

専用テスト環境で次をすべて実演できた場合、P0を技術的に成立とする。

1. 最初の管理者を一度だけ登録し、ログインできる。
2. Filma APIキーを設定し、固定したFilma APIへの接続を確認できる。
3. 既存のFilma動画を一件登録し、一つの使い切りコードを発行できる。
4. 未ログインの視聴者がコードを一度だけ使用して動画を再生できる。
5. 同じコードを別セッションまたは並行要求から再利用できない。
6. 視聴者が一時視聴中に登録またはログインすると、その動画の視聴権がアカウントへ移る。
7. 再ログイン後、期限内の動画だけが視聴可能一覧に表示され、再生できる。
8. 視聴者向けの全ルートで、非公開、公開前、期限終了後の動画についてタイトル、説明、Filma識別子、再生情報を取得できない。
9. Cloudflare WorkersとD1へ手動デプロイし、3〜5名の招待テスターが試せる。

利用価値はアプリ内解析を追加せず、テスト観察で確認する。テスターの80%以上が補助なしで「コード入力から再生」まで完了できることを初期目標とする。個人情報やAPI応答をIssueへ記録せず、成功・失敗した工程と改善点だけを残す。

## P0の範囲

### 管理者

- 最初の管理者一名の初期登録、ログイン、ログアウト
- Filma APIキーの登録、再設定、接続状態の確認
- 既存Filma動画の手動登録と編集
- 動画ごとの公開状態、公開開始日時、公開終了日時の設定
- 動画ごとに一つずつ使い切りコードを生成
- 未使用・使用済み・失効の状態と使用日時だけを確認

管理者は期限終了後を含む全動画を管理画面で確認・編集できる。管理者プロフィール、複数管理者、コード一括生成、コードの再表示は実装しない。

### 視聴者

- タイトルなどを表示しないコード入力ページ
- 有効なコードによる一時視聴
- 再視聴には登録またはログインが必要という明確な警告
- メールアドレスとパスワードによる登録、ログイン、ログアウト
- 一時視聴権のアカウントへの引き継ぎ
- 期限内の視聴可能動画一覧と再視聴

P0ではメールアドレスの所有確認、メール送信、パスワード再設定を実装しない。登録メールアドレスはログイン識別子であり、確認済み本人情報とは扱わない。テスト用の値だけを使用する。

### 動画

- CMSにはFilma動画ID、タイトル、説明、公開状態、公開開始日時、公開終了日時だけを保存する。公開状態は`draft`と`published`の二つとし、視聴可能条件を「`published`かつ公開開始日時以上かつ公開終了日時未満」に固定する。
- 動画ファイル、サムネイル、字幕、FilmaのJWTまたは再生URLは保存しない。
- 動画アップロード、アクセス解析、DRM設定は実装しない。
- サムネイルを扱わないため、一覧はタイトルと期限だけのテキスト表示とする。

## 主要フロー

### 管理者の初期設定

1. 運用者がCloudflare Worker secretとして256 bit以上の`PLAY_BOOTSTRAP_TOKEN`を登録してから公開する。
2. 管理者が初期登録画面を開き、bootstrap token、メールアドレス、パスワードを入力する。
3. サーバーがtokenを固定時間で検証し、管理者未登録かつbootstrap未使用であることを確認する。
4. サーバーが管理者一件の作成とbootstrap使用済み状態の保存を同一トランザクションで行う。
5. 管理者がログインし、Filma APIキーを入力する。
6. サーバーが固定Filma endpointでキーを検証し、暗号化済みキーと必要最小限の接続情報を保存する。
7. bootstrap tokenとAPIキーは保存後に画面へ再表示しない。

requestのbootstrap tokenが未指定・不一致・使用済みの場合と、管理者が存在する場合は、理由を区別しない404として初期登録APIを閉じる。DBがbootstrap未使用なのにWorker secret自体が設定されていない場合だけ、構成不備として503にする。使用後はWorker secretを削除し、通常routeはそのsecretなしで動作させる。初期登録APIはDBの使用済み状態により、secretの有無や古い値にかかわらず汎用404を返す。

### 動画登録とコード発行

1. 管理者が既存Filma動画ID、タイトル、説明、公開開始・終了日時を入力する。
2. サーバーがFilma動画の存在と再生可能性を確認してから保存する。
3. 管理者が動画を公開状態へ変更する。
4. サーバーが暗号学的乱数から16文字のCrockford Base32コードを生成し、`XXXX-XXXX-XXXX-XXXX`形式で一度だけ表示する。
5. DBには正規化したコードのSHA-256ハッシュだけを保存する。

コードは管理者が一件ずつ発行する。紛失時は既存コードを再表示せず、未使用コードを失効させて新しいコードを発行する。

### 未ログイン視聴者の初回視聴

1. 視聴者が動画ごとの公開URLを開く。
2. ページは動画タイトルを表示せず、コードだけを求める。
3. サーバーは公開状態、公開期間、コードの未使用状態を同一トランザクション内で確認し、コードを原子的に消費する。
4. サーバーは30分間の匿名視聴セッションを発行する。
5. 画面は動画を再生し、「30分以内に登録またはログインしない場合、この動画は再視聴できない」と表示する。

匿名視聴セッションは同じブラウザーでの再生開始、プレイヤー再読込、登録・ログインへの遷移にだけ使用する。30分経過、Cookie削除、別ブラウザーへの移動後は復元しない。

### 登録済み視聴者と視聴権の引き継ぎ

- ログイン済み視聴者がコードを使った場合、コード消費と同じトランザクションで視聴権をアカウントへ付与する。
- 未ログイン視聴者が匿名視聴セッションの有効中に登録またはログインした場合、そのセッションの視聴権を一度だけアカウントへ移す。
- 同じ動画の視聴権が既にある場合は重複行を作らない。
- 視聴権は動画の公開状態と公開期間を上書きしない。動画が非公開または期間外なら再生できない。

### 視聴可能動画一覧

1. 視聴者がログインする。
2. サーバーがアカウントの視聴権と動画の公開状態・期間を結合して判定する。
3. 現在視聴可能な動画だけについて、public ID、タイトル、説明、公開終了日時を返す。
4. 非公開、公開前、期限終了後の動画は件数にも含めない。

## 画面

P0は次の画面だけを持つ。デザインシステムや高度な管理テーブルは作らない。

- `/admin/setup`: 初期管理者登録
- `/admin/login`: 管理者ログイン
- `/admin/filma`: APIキー設定と接続状態
- `/admin/videos`: 動画一覧、登録、編集、コード発行
- `/v/:publicId`: コード入力、匿名視聴、登録・ログイン警告
- `/login`: 視聴者ログイン
- `/register`: 視聴者登録
- `/library`: 視聴可能動画一覧

管理者と視聴者は同じ認証基盤を使うが、サーバー側のrole判定でAPIと画面の権限を分ける。

## データモデル

P0のD1テーブルを次に限定する。

- `accounts`: ID、role、正規化メールアドレス、パスワードハッシュ、作成日時
- `sessions`: セッションIDのハッシュ、アカウントIDまたは匿名、失効日時、作成日時
- `app_settings`: bootstrap使用日時、暗号化済みFilma APIキー、organization ID、API type、最終確認日時
- `videos`: 内部ID、推測困難なpublic ID、Filma動画ID、タイトル、説明、公開状態、公開開始・終了日時
- `access_codes`: ID、動画ID、コードハッシュ、発行日時、取消日時
- `redemptions`: コードID、動画ID、匿名セッションID、引き継ぎ先アカウントID、使用日時
- `entitlements`: アカウントID、動画ID、元コードID、付与日時
- `rate_limits`: endpointと匿名化bucketごとの固定窓・試行数
- `migrations`: 適用済みスキーマ番号

一つのコードに対して`redemptions`は一件だけ、同じアカウントと動画に対して`entitlements`は一件だけとし、DB制約と単一トランザクションで保証する。未使用コードは管理者が取り消せるが、動画の公開期間を越えて有効にはならない。アクセス履歴や再生回数は保存しない。

## Filma APIの事前検証

実装前に、専用テスト組織と既存テスト動画だけを使う4時間上限の技術調査を独立Issueで行う。

確認対象は次に限定する。

- 既存動画をAPIで識別・確認する方法
- ブラウザーで再生するために必要なAPIまたは埋め込み契約
- 再生情報の検証可能な有効期限とドメイン制限
- readonly APIキーで可能な操作
- エラー形式、リダイレクト、最大応答量

公式資料または実レスポンスで確認できた項目だけを契約テストへ記録する。APIキー、JWT、organization ID、動画ID、再生URL、レスポンス本文は記録しない。送信先はコード内の許可リストへ固定し、5秒タイムアウト、64 KiB応答上限、自動再試行なしを適用する。

再生契約のGO条件は、再生情報に検証可能な非null有効期限があり、CMSが指定する`notAfter`以前に失効させられ、許可済みCMSドメイン以外で利用できないことである。CMSは`notAfter`を「現在時刻から5分後」と「動画の公開終了日時」の早い方に固定し、それを超える再生情報を拒否する。既発行の再生情報も動画期限後に利用できないことを実演または公式仕様で確認する。

4時間でこの有効期限・ドメイン制限を含む安全な再生契約を確認できない場合は推測実装やHTMLスクレイピングを行わず、再生と試験公開を停止してFilma側のAPI追加または仕様提供を判断する。2026-09-07承認の[追補](../../development/admin-first-prototype.md)に限り、実動画公開を無効にしたlocalhost用管理機能を先行できる。

## コンポーネントと実行環境

- HTTP/API: Hono Worker
- 管理画面・視聴画面: React + Viteの単一ビルド
- DB: Cloudflare D1
- 暗号: Web Crypto
- 動画配信: Filma
- デプロイ: `wrangler`による手動デプロイ

ドメインルールとFilmaクライアントは既存基盤設計のポート境界を維持する。P0ではNode.js、SQLite、ローカルストレージ、R2、Docker、Deploy to Cloudflareボタンを実装しない。完成版でアダプターを追加できるよう、Cloudflare固有型をcoreとapplicationへ持ち込まない。

## API境界

公開APIを次に限定し、未定義ルートは404とする。

- 初期設定・認証: 管理者初期登録、管理者・視聴者ログイン、視聴者登録、ログアウト
- 管理者: Filma設定、動画一覧・作成・更新、コード生成・失効
- 視聴者: コード消費、再生情報取得、視聴権一覧

状態変更はJSONのみを受け付け、16 KiBを上限とする。入力は境界で検証し、余分なフィールドを拒否する。初期管理者登録はbootstrap未使用の間だけ`PLAY_BOOTSTRAP_TOKEN`、管理APIはadmin role、視聴権一覧はviewer role、再生情報は有効な匿名視聴セッションまたはviewer entitlementを必須とする。

## セキュリティと失敗時の挙動

- パスワードは標準パスワードハッシュ、Filma APIキーはWeb Cryptoで暗号化、セッションIDとコードはハッシュだけを保存する。
- Cookieは`HttpOnly; Secure; SameSite=Lax; Path=/`とし、セッション失効日時をサーバー側でも確認する。
- 状態変更APIは同一Originを要求する。
- ログイン、登録、コード入力、再生、Filma接続にはD1共有のレート制限を適用し、D1障害時は503として安全側に閉じる。
- コードの存在、使用済み、動画の非公開、期間外を外部向けには同じ汎用エラーとして扱う。
- 匿名状態では有効なコードを消費するまで動画メタデータを返さない。
- 再生要求ごとに公開状態、公開期間、セッションまたは視聴権をサーバー側で再確認する。
- Filmaの再生JWTまたは署名URLは要求時に`notAfter`を指定して取得し、非null有効期限が`notAfter`を超えないことを検証する。DB、ログ、ブラウザー永続ストレージへ保存しない。
- 視聴者向けルートでは、非公開、公開前、期限終了後は404を返し、タイトル、説明、Filma動画ID、再生情報を応答しない。認証済み管理者の管理APIでは状態確認と編集に必要なメタデータを返す。
- APIキー、パスワード、コード、Cookie、認証ヘッダー、Filma応答本文をログとエラーへ含めない。

P0は招待テスト専用であり、一般公開、実顧客データ、本番Filma組織、課金、SLAを対象としない。

### レート制限契約

本番のclient bucketはCloudflareが設定した`CF-Connecting-IP`を、Worker secret `PLAY_RATE_LIMIT_KEY`によるHMAC-SHA-256へ通し、先頭16 byteをbase64url化して作る。headerが本番で欠落した場合は503とし、任意のforwarded headerへfallbackしない。accountや動画を使うbucketも生値ではなく同じkeyed HMACで作る。

- 初期登録: clientごとに15分5回
- ログイン: clientごとに15分10回、対象accountごとに15分5回
- 視聴者登録: clientごとに1時間3回
- コード入力: clientごとに10分10回、対象public IDごとに10分5回
- Filma接続確認: admin accountごとに10分5回
- 再生情報取得: 匿名sessionまたはviewer accountごとに1分60回

固定窓の更新は一つの原子的UPSERTで行い、複数bucketがあるendpointはすべて通過した場合だけ処理を続ける。超過時は窓終了までの秒数を`Retry-After`へ返す。bucket行は窓終了24時間後を削除期限とし、各更新時に期限切れ行を最大100件だけ削除する。テストではClockとclient bucket providerを依存注入し、実IP headerを偽装しない。

## エラー処理

- 入力不正は400、未認証は401、認証済みだが権限不足は403とする。
- 外部へ存在を隠す必要がある動画・コードの状態は404の汎用応答へ統一する。
- レート制限超過は`Retry-After`付き429、レート制限判定不能は503とする。
- Filma認証失敗、到達不能、契約不一致は秘密情報を含まない管理者向け分類へ変換する。
- Filma再生情報を取得できない場合は503とし、過去の再生情報へフォールバックしない。
- DBまたは暗号化処理の失敗時は状態を部分保存せず、相関IDだけをログへ残す。

## テスト

### 単体・契約テスト

- 最初の管理者を一度しか作れない。
- bootstrap tokenが未指定・不一致・使用済みの場合に初期管理者を作れず、並行要求でも一件だけ作成される。
- パスワード、APIキー、セッションID、コードが平文保存されない。
- コードの並行消費で一件だけ成功する。
- 匿名視聴権の引き継ぎが一度だけ成功する。
- 同じ動画の視聴権を重複保存しない。
- 公開状態と公開期間の境界時刻をサーバー時刻で判定する。
- Filmaクライアントが固定送信先、リダイレクト拒否、5秒、64 KiB、単一試行を守る。
- Filma再生情報の有効期限が非nullで`min(現在+5分, 動画終了)`を超えず、過去に発行した情報でも動画期限後に再生できない。

### 統合・E2Eテスト

- 管理者初期登録から動画・コード作成まで。
- 未ログインのコード入力から匿名再生まで。
- 匿名視聴中の登録からライブラリ再視聴まで。
- ログイン済み視聴者によるコード消費とライブラリ追加。
- 使用済みコードの別セッション・並行要求による再利用拒否。
- 非公開、公開前、期限終了後のメタデータと再生情報の非開示。
- レート制限、入力上限、Origin、role境界の負系。

実Filma APIテストは明示実行に限定し、通常テストと公開CIから分離する。実APIテストは既存動画の参照と再生契約だけを確認し、Filma上のデータを作成・更新・削除しない。

## P0で延期するもの

- CMSからFilmaへの動画アップロードと自動連携
- アクセス解析と視聴イベント保存
- DRM設定
- サムネイルと字幕
- 管理者プロフィールと複数管理者
- メール確認、通知、パスワード再設定
- コード一括生成、CSV出力、再利用可能コード
- Node.js、SQLite、ローカルストレージ、R2、Docker
- Deploy to Cloudflareボタン
- 一般公開向けバックアップ、監視、SLA

延期は削除を意味しない。P0のテスト結果を確認した後、利用価値または運用上の必要性が高い順に独立Issueとして扱う。

## 実装の分割方針

仕様承認後、実装計画では大きな水平レイヤーではなく、動作する状態を保つ小さな縦切りに分割する。

1. PR #7を最新`develop`へ同期し、Filma認証契約を再レビューしてmergeする。
2. Filma既存動画・再生契約を4時間で調査する。
3. Cloudflare起動、D1、単一管理者認証をつなぐ。
4. 既存動画登録、コード発行、匿名視聴をつなぐ。
5. 視聴者登録、視聴権引き継ぎ、ライブラリをつなぐ。
6. 期限切れ情報遮断の負系とCloudflare試験公開を完成させる。

各項目を一つのIssue、一つのfeature branch、一つのPRとして扱い、独立レビュー可能な大きさに保つ。

## P0終了時の判断

- 技術的に成立し利用者が迷わない場合: 動画アップロード、解析、国内サーバー対応の優先順位を決める。
- 技術的に成立するが利用者が迷う場合: APIやデータモデルを増やさず、画面と文言を改善する。
- Filma再生契約が成立しない場合: CMS側で迂回実装せず、Filma APIの追加要件を整理する。
- 利用価値が確認できない場合: 完成版の追加実装を止め、対象利用者と共有フローを見直す。
